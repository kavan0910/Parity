Benefits

Evidence you can check at every step, from the first map to the last slice

Evidence on every claim

Each node and edge carries a file and line range. Evidence that does not exist in the code is dropped before it reaches the doc.

A Verifier that never sees your code

It compares the generated doc with your own requirements docs and reports contradictions, doc only items and code only gaps. Every quote is string checked.

An approval you sign, and that expires

status lists what blocks approval. approve writes a fixed copy of the doc and a migration contract. If the graph changes later, the approval turns stale.

Expected results from the real service

Tests are recorded from your running legacy service, twice, with noise masked. The model proposes inputs and never writes an expected answer.

The model edits, the sandbox runs

The model returns file edits and never gets a shell. Builds and tests run in Docker: tests with no network, builds through your package mirror, no secrets.

Your model, your budget

Any provider LiteLLM supports, set per task. --max-usd stops a run gracefully, and a re run of unchanged code makes zero model calls.

Every claim points to a line of code. Every migrated slice is checked against what the old service actually returned.

How it works

Three steps from source folder to migrated service

01

Map the service

Copy the source into a project, redact secrets and pull static facts. The model then reads the code in chunks and returns nodes, edges and business rules, each checked against the real file and line.

migration-agent init ./svc
migration-agent ingest svc.migration
migration-agent extract svc.migration
migration-agent analyze svc.migration \
  --config gemini.config.json --max-usd 1
02

Check it and approve it

Run the Verifier against your docs and resolve or defer each finding. Mark every quirk or suspected bug to preserve (the default) or fix. Approval is refused while any blocker is open.

migration-agent verify svc.migration
migration-agent resolve svc.migration \
  F-0001 --status accepted_code
migration-agent decide svc.migration \
  RULE-0003 --fix
migration-agent status svc.migration
migration-agent approve svc.migration \
  --by "Your Name"
03

Migrate with proof

Describe the target, plan slices from the approved contract, then generate and verify one slice at a time. Each slice waits for your approval. See the four stages

migration-agent target init \
  svc.migration --runtime 21 \
  --framework spring-boot@3.3
migration-agent plan svc.migration
migration-agent generate \
  svc.migration --slice SLICE-0001
Migrate with proof

A slice ships only when it answers like the old service

The migration starts from your approved contract and moves one slice at a time. The first supported target is Java 8 with Spring Boot 2 to Java 21 with Spring Boot 3.

Beta. Every stage below is built, covered by automated tests, and has run in a real Docker sandbox on three sample services. It has not yet run with a real model, so the quality of model-written code is unmeasured.

  1. Check the target fits

    target fit reads fixed library tables for Java 8 to 21, Spring Boot 2 to 3, Django 3.2 to 5, Express to Fastify and JavaScript to Go. Risks the model adds are kept only when their cited evidence exists.

  2. Record what the old service does

    The planner cuts the service into slices in dependency order. The model proposes test inputs, each case runs twice against the live legacy service, and the recorded response becomes the expected result. Services that need a token get the sandbox's random one on every request.

  3. Generate inside a sandbox

    The model returns structured edits and never gets a shell. Builds and tests run in Docker, and a reviewer in a fresh session checks the slice without the generation history.

  4. Prove it, approve it, flip it

    Both services restart from the same data and run the same cases, and every difference is listed. A fuzzer and a latency check add advisory warnings. You approve each slice, the strangler fig router moves its routes, and the cutover plan needs its own approval, in the review UI or the CLI.

One case, two servicesequivalence run

Config keys are mapped to the target convention with secrets written as references only. metrics reports cost per slice and how often people had to edit the generated code.

Where it stands today

Available

Understand and approve

Map, verify, review and approve a service from the CLI. It ran end to end on the three repos above.

Beta

Migrate with proof

Built, tested, and run in a real Docker sandbox on three samples. Not yet run with a real model, so generated-code quality is unmeasured.

CLI only

Runs on your machine

Use it as a CLI on your own hardware. No hosted service is available, and you bring your own model key.

Try it before you spend anything: analyze --dry-run prints the plan and a cost estimate without a model call, and --max-usd stops any run at your limit while keeping partial results.

Quickstart

Map your own service, then try the migration beta

Needs Python 3.11 or newer and an API key for the model you choose. Put the key in a .env file in the project root, never on the command line. The migration steps also need Docker.

terminal
# get the source: {{repository url}}
pip install ".[llm]"
cp .env.example .env   # add GEMINI_API_KEY or ANTHROPIC_API_KEY

# 1. understand
migration-agent init ./my-service
migration-agent ingest my-service.migration
migration-agent extract my-service.migration
migration-agent analyze my-service.migration --dry-run   # estimate first
migration-agent analyze my-service.migration --config gemini.config.json --max-usd 1
migration-agent review my-service.migration

# 2. approve
migration-agent status my-service.migration
migration-agent approve my-service.migration --by "Your Name"

# 3. migrate (beta, needs Docker; set request_headers in harness.yaml if your service needs a token)
migration-agent doctor my-service.migration
migration-agent target init my-service.migration --runtime 21 --framework spring-boot@3.3
migration-agent target fit my-service.migration --max-usd 1
migration-agent plan my-service.migration
migration-agent harness import-source my-service.migration --from-original
migration-agent harness build my-service.migration --legacy
migration-agent harness up my-service.migration --legacy
migration-agent tests generate my-service.migration
migration-agent tests record my-service.migration --harness
migration-agent generate my-service.migration --slice SLICE-0001
migration-agent harness build my-service.migration --new
migration-agent harness up my-service.migration --new
migration-agent equivalence run my-service.migration --slice SLICE-0001
migration-agent equivalence fuzz my-service.migration --slice SLICE-0001   # advisory
migration-agent approve-slice my-service.migration SLICE-0001 --by "Your Name"
migration-agent cutover my-service.migration   # readiness + plan; approve it in the review UI or with --approve

FAQ

Questions before you try it

Does it change my code?

No. Ingest copies your source into a project folder, and analysis reads that copy only. The migration writes the new service into target_code/ inside the project folder as git commits, so your repository is never edited. Archives and git sources are validated for path traversal, symlink escapes and decompression bombs.

Does the model run any code?

No. While migrating, the model returns structured file edits and nothing else. It has no shell, exec or network tool. The tool applies the edits, then builds and tests run in a Docker sandbox: tests with no network at all, builds with access only to the package mirror you configure.

Where does the expected behaviour come from?

From your running legacy service. The model only proposes test inputs. Each case runs twice against the old service, values that differ between the two runs are masked as noise, and the recorded response becomes the expected result. For a quirk you chose to fix, you approve the specified result instead.

What happens to secrets?

Ingest redacts credential patterns and withholds key and environment files before anything reaches a prompt, a cache or a document. Recorded results mask values that look like secrets, sandbox jobs refuse secret environment values, and the config map writes secrets as references such as ${DB_PASSWORD}, never as values. Redaction is pattern based, so unusual secrets can still slip through. The threat model lists this as a known risk.

Which migrations does it support?

The first supported target is Java 8 with Spring Boot 2 to Java 21 with Spring Boot 3. Library tables also cover Django 3.2 to 5, Express to Fastify and JavaScript to Go, but the Java path is the one being finished first.

Is the migration phase production ready?

It is in beta. It is built, tested, and has run in a real Docker sandbox on three sample services, but it has not yet run with a real model, so the quality of model-written code is unmeasured. Run it on a copy and review every slice before you approve it.

What does approval lock in?

approve is refused while coverage is incomplete, a Verifier finding is unresolved, a re analysis or comment is pending, or the doc on disk is out of date. On success it writes a read only copy of the doc and docs/migration_contract.json with your preserve or fix decisions and any deferred findings. A later change to the graph makes the approval stale.

Which languages and frameworks does it understand?

Python, JavaScript, TypeScript, Java, Go and C# files are parsed into syntax trees. Files in other languages such as COBOL, Ruby or PHP are recognised but not parsed. Route extractors cover Express, Spring, Flask, FastAPI, Django, Rails and ASP.NET. Schema extractors cover Flyway, Alembic, Prisma and TypeORM, and OpenAPI and proto files are parsed.

Which models can I use, and what does a run cost?

Any provider LiteLLM supports, chosen per task in a config file or with MA_* environment variables. We have run it with Gemini models; the Anthropic sample configs are included but untested. Mapping the three small repos above cost between $0.021 and $0.077. Run analyze --dry-run for an estimate first.

Does anything leave my machine?

Only the calls to the model endpoint you configure, a git clone if your source is a git URL, and in the migration phase, build jobs that reach your package mirror. Test jobs run with no network. The review server binds to 127.0.0.1 with a per run token.

Can it handle a large repository?

Chunk planning handled a synthetic 2,420 file repo in about a tenth of a second in our tests, and incremental runs re analyze only changed files and their direct importers. We have not run a model over a repo that size yet.
