Parity / user guide
Legacy app migration · web app and CLI

Migrate the legacy app you have to the stack you want.

Parity takes an existing legacy application and migrates it to the newest version of its stack, or to a different technology, and proves the new app behaves like the old one. This guide covers the hosted web app, which runs step 1 of that migration (understanding the legacy app), page by page, with the matching command-line steps for everything after it. It also tells you plainly what the tool can and cannot see.

Read this first

The hosted platform is in development. It is not a released or audited service, there is no billing, and several things people expect from a SaaS product (single sign-on, private repositories, e-mailed invitations, password reset) are not built. Every such gap is marked Not available yet where it matters and collected in one list. Where the web app has no button for something that the server can do, this guide shows the API or CLI route instead and says so.

01What the product does, and who it is for

The MVP

Legacy app in, migrated app out, with proof. Point the tool at an existing application, choose the target (a newer version of the same stack, or a different technology), and get a migrated application, an equivalence report against the running legacy app, and a cut-over plan. Targets covered today: Java 8 to 21, Spring Boot 2 to 3, Django 3 to 5, Express to Fastify, JavaScript to Go. The migration has five steps: understand, approve, migrate, prove, cut over. Understanding the legacy app is step 1, not the goal.

Parity migrates a legacy application in five steps. This web app runs the first: it reads the source code of the legacy service and produces two things, an understanding document (readable prose organised into fixed sections such as endpoints, data model, business rules and quirks) and a knowledge graph of the things it found. Every claim in both points at a file, a line range and a verbatim quote from your code, and the quote is machine-checked against the real file before the claim is kept. That map is what the later steps (approve, migrate, prove, cut over, in the command-line tool) are built on.

A second pass, the blind Verifier, compares that code-derived document with the documentation your team already has (requirements, wikis, runbooks) and lists where they disagree. You decide who is right; some of your answers trigger a targeted re-analysis, which produces a new graph version.

Who it is for

Engineers and tech leads who must move a legacy service to a newer version or a different stack, often one they did not write.

What you get here

Step 1 of the migration: a cited document, a browsable graph with evidence quotes, and a reviewable list of doc-versus-code disagreements. The migration itself runs in the CLI.

What it never does

Execute your code, modify your source, or let the model write outside a read-only, path-jailed view of the ingested copy.

What it is not (yet)

A finished, audited product. The migration steps are a command-line beta that has not run with a real model. The map is a well-cited reading aid, not a proof of correctness. See reading results honestly.

Two ways to use it

Web app versus CLI
Web app (hosted)CLI (migration-agent)
Teams, shared review, roles, audit log, usage metering. You never see an API key: the operator's server holds it. You choose a model profile (Fast, Balanced, Best), not a model name. One engineer, one machine. All state lives in a single <name>.migration folder. You bring your own model API key and pick models with a config file. Includes a local review UI bound to 127.0.0.1.

Both run the same engine, so results are comparable. The CLI is described in docs/user-guide.md; this guide gives the CLI equivalent of every web step in the CLI table.

02Quickstart: first result in about five minutes

You need the web app's address from whoever runs your deployment (locally it is http://localhost:3000) and a public https git repository, or a .zip / .tar.gz of your code.

  1. Create an account. Open the app, choose Start free (or go to Sign up), enter a work email and a password of at least 10 characters, and press Create workspace. You land on Projects, signed in, as owner of a new workspace. If sign-up is closed on your deployment you will see "sign up is disabled": ask your operator for an account.
  2. Connect a service. Press New project. Give it a name, keep Git URL selected, paste a repository such as https://github.com/spring-projects/spring-petclinic, and press Create project.
  3. Look at the estimate. On the project's Overview tab, Start a run already shows an Estimate before you start (chunks to read and an estimated cost) and either Allowed on your plan or Not allowed. Leave Run type on Analyze and Model profile on Balanced. Set Budget cap (USD) to something you are comfortable losing.
  4. Start the run. Press Start run. A live panel shows stages (ingest, extract, analyze), spend against your cap and a log. A small service finishes in about a minute; a large one can take much longer and is limited by the model provider's rate limits.
  5. Read the result. When the status pill turns Succeeded, press Read the document for the prose, or Explore the graph and click any node to see its evidence quotes and confidence.
  6. Optional: check it against your own docs. Upload your documentation (this is an API step today), start a run of type Verify: compare with your docs, then open the Findings tab and answer each disagreement.
Same thing in the CLI 
pip install ".[llm]"                         # needs Python 3.11+
cp .env.example .env                         # add ANTHROPIC_API_KEY or GEMINI_API_KEY

migration-agent review  petclinic.migration                  # local review UI

03Core concepts

The pipeline, and why the Verifier is "blind"

Vocabulary you will see in the app

Workspace
Your team's container. Holds projects, members, usage and limits. Choose it in the Workspace selector in the left bar. Signing up creates one and makes you its owner.
Project
One legacy service: one source (git URL or archive), its runs, its graph versions, findings, comments, and your uploaded docs.
Run
One background job on a project. Types: analyze (ingest, extract, analyze), verify (blind Verifier) and reanalyze (re-read only what review changed). Statuses: Queued Running Succeeded Failed Stopped at budget Cancelled. Only one run of each type can be queued or running per project at a time.
Snapshot / graph version
Each successful analysis or re-analysis saves an immutable graph snapshot, v1, v2 and so on. Node IDs stay stable across versions (a registry maps a node's type, module and symbol to its ID), so versions diff cleanly.
Node
One thing found in the code. Every node has an ID, a type, a name, a module, a plain-language responsibility, evidence, a derived confidence and two optional flags: quirk (odd behaviour worth preserving on purpose) and suspected bug.
Edge
A relationship between two nodes. Types: calls, reads, writes, depends_on, publishes, consumes, implements, configures. Edges carry evidence and confidence too.
Evidence
A file path, optional line range and symbol, and a verbatim quote. The quote is checked against the real file; claims whose quotes do not match are rejected or demoted.
Confidence
Derived from evidence, never asserted by the model. See the table below.
Finding
A disagreement the Verifier found, with a title, severity (high, medium, low), explanation, verbatim quotes from both sides and links to related nodes.
Resolution
Your answer to a finding, one of four statuses. See Review findings.
User docs
Your existing documentation files. They are used only by the Verifier.
Blind Verifier
The comparison step that sees exactly two inputs: the generated document and your docs. It never sees code and the analysis never saw your docs.

Node types

The engine knows nine node types; the explorer's filter chips offer the first six.
TypeID prefixMeaningFilter chip

How confidence is derived

An evidence item is strong when it has a verbatim quote and is pinpointed by a line number or a symbol name. Confidence is then computed, not guessed:

Derived confidence levels
LevelRuleHow to read it
highAt least two strong evidence itemsTwo independent, pinpointed, verified quotes agree. Still a reading of code, not a test result.
mediumOne strong item, or two or more weaker onesReasonably grounded; worth a glance at the quote.
lowOne weak item (for example a quote without a line or symbol)A lead, not a fact. Check the quote yourself.
noneNo evidenceListed under "Blind Spots / low confidence" in the document. Do not rely on it. (The explorer's meter is drawn for low, medium and high; a none node may show an empty meter.)
Why low is common

In the first measurements, no node reached "high" and most were "low". That can mean the evidence bar is strict, which is good for trust, or that the model is not yet supplying strong evidence, which is bad for usefulness. It has not been resolved. Low is not the same as wrong. See reading results honestly.

What the understanding document contains

The document is rendered from the graph into fifteen fixed sections: Purpose and Capabilities; Boundary and External Dependencies; Component Responsibilities; Endpoints and API Surface; Data Model and Storage; Business Rules; Integrations and Contracts; Background Jobs and Consumers; Configuration and Environment; Auth, Error Handling and Cross-Cutting; Existing Tests; Quirks and Suspicious Code; Blind Spots / low confidence; Open Questions and Assumptions; and a Coverage Matrix that shows which inventory items (files, routes, config keys, dependencies) were accounted for. Read sections 13 to 15 first if you want to know what the tool is unsure about.

04Sign up and log in

Sign up. Go to the sign-up page (from the landing page choose Start free). Fields: Name (optional), Work email, Password (at least 10 characters; the form says "Use at least 10 characters." otherwise). Press Create workspace. This creates your account and a default workspace in which you are the owner.

Log in. Choose Log in, enter email and password, press Log in. Too many failed attempts for one email trigger a growing wait ("too many failed sign-in attempts, try again later").

Sign out. Sign out is at the bottom of the left bar (in the menu on a phone). The theme button next to your name switches light and dark.

Sessions are short

The access token lives only in the page's memory and expires after about an hour by default. A page reload or an expired token sends you back to Log in. There is no silent refresh. Unsaved text (a half-written comment) is lost. Operators can enable tab-scoped persistence, so a reload may keep you signed in on some deployments.

Not available yet

Single sign-on / OIDC login in the web UI, password reset, e-mail verification and account deletion. The UI uses the built-in password sign-in only. If you forget your password, ask your operator.

Closed sign-up

In production, self-service sign-up is off by default and the server answers 403 "sign up is disabled". Your operator then creates accounts for you. A workspace owner or admin can still invite colleagues who already have an account (see Members and roles).

CLI equivalent

None needed: the CLI has no accounts. You supply a model API key through the environment or a .env file.

05Create a project

From Projects press New project (or Connect a repository on an empty workspace). The page is titled Connect a service, "Step 1 of 2". Viewers do not see the button.

  1. Project name. 2 to 80 characters, for example orders-service.
  2. Source. Choose Git URL or Upload archive.
  3. Press Create project. The project is created, then the source is attached. You land on its Overview. If attaching the source fails, the project already exists; fix the source and submit again (the form says "Project created. Fix the source and submit again to continue.").

Git URL

Field Repository URL: "Public https URLs only. Private, loopback and link-local hosts are rejected."

  • Scheme must be https://; port must be 443 (or omitted).
  • No credentials in the URL, no query string, no fragment.
  • The host must resolve to a public address. localhost, .local, .internal, private ranges, link-local, loopback and numeric hosts are refused. Operators may further restrict hosts to an allowlist.
  • The repository is cloned shallowly when you first estimate or run, not when you press Create. That clone is then frozen as your project's source snapshot. Later commits to the remote do not show up until you replace the source (see Re-analysis and incremental).
Not available yet

Private repositories, GitHub/GitLab app integration, SSH URLs and access tokens. If the repository is private, the clone fails with "git clone failed (repository not found or not public)". Workaround: download an archive yourself and use Upload archive.

Upload archive

Field Archive: drop a file or press Choose file. Accepted: .zip, .tar.gz, .tgz. The page checks the name and says "Use a .zip, .tar.gz or .tgz archive." Its size check says 200 MB, but the server's limit is the one that counts: 100 MB by default (and never more than your plan's source-size limit), so a file between 100 and 200 MB passes the page and is then refused with "file exceeds 100 MB". Prefer a clean archive without build output.

What the server rejects in an archive, and why
Message you may seeWhy it is refused
unsupported archive type (use .zip or .tar.gz)Only zip and tar.gz are read.
archive is corrupt or unsupported (...)The file could not be parsed.
encrypted archives are not supportedThe server cannot read password-protected zips.
archive contains links or special filesSymlinks, hard links and device files could point outside the archive.
archive contains a path traversal entry / an absolute or backslash path / an invalid entry nameEntries like ../../etc/x or /etc/x would write outside the sandbox.
archive contains too many files / too many entries / duplicate entriesDefault ceilings: 50,000 files, 100,000 entries in total (directories count), no duplicate paths.
archive contains a file that is too largeA single file over 50 MB by default.

archive paths are nested too deeplyDirectory depth over 64.
archive processing exceeded the time limitValidation has a wall-clock cap.
archive is emptyNothing to analyse.

Separately, the engine's ingest step decides what is actually analysed. It skips symlinks, binaries, files over 1 MB and vendor or build directories (.git, node_modules, vendor, build, dist, target, virtualenvs). Credential files such as .env, *.pem, id_rsa and .npmrc are withheld entirely, and secrets found inside other files are replaced with [REDACTED:<kind>] before anything reaches a prompt. Redaction is pattern based, so an unusual secret format can slip through; do not rely on it as your only control. Skipped files appear as blind spots, not as findings.

CLI equivalent 
migration-agent init ./legacy-orders                    # directory, .zip, tarball or git URL
migration-agent init https://example.com/team/orders.git --project ./orders.migration --name "Orders service"
migration-agent ingest legacy-orders.migration           # prints what was copied and skipped; see ingest_report.json

06Cost estimate, budget cap and model profiles

Nothing is spent until you press Start run. The Estimate before you start box updates as you change the profile, run type or the Incremental checkbox. It comes from a real dry run of the engine's chunk planner on your source.

Reading the estimate

  • estimated: predicted model spend in USD. It is a planning figure computed from token counts and the configured model prices, not a quote.
  • chunks to read: how many token-bounded pieces of code the model will read. More chunks means more time and cost.
  • Allowed on your plan or Not allowed, with a reason underneath when not allowed. The reason comes from your workspace limits, for example "requested budget exceeds the per-run limit of the plan" or "monthly spend limit would be exceeded (spent plus budget reserved by runs in progress)". Start run stays disabled until the run is allowed.
  • If your cap is lower than the estimate you get a warning: "The run will stop early and give a partial result."
Know the estimate's limits

The estimate is the analysis chunk plan. For Verify and Re-analyze runs it is only a rough guide. In the first measurements the whole pipeline ran as one chunk per small repository, so how well the estimate tracks reality on large repositories has not been measured yet.

Budget cap (USD)

A hard ceiling for this run. When spend reaches it the run stops gracefully (status Stopped at budget), keeps what it has and publishes the partial result. Starting another run later reuses cached model responses and checkpoints, so finished work is not paid for twice. The page pre-fills 1.00.

  • The field hint says "Empty means no cap beyond your plan." In practice, the server then applies its default per-run budget (5 USD in the standard configuration), not "unlimited". Always type a number.
  • The cap must be above zero and at most the server's hard ceiling (200 USD by default). Your plan can set a lower per-run cap.
  • The full cap is reserved against your workspace's monthly budget while the run is queued or running, even if it ends up spending less.

Model profile: Fast, Balanced, Best

You choose a profile; the server maps it to specific models and injects its own API key. You never see or choose raw model names. The profile decides which tier each task uses:

Which model tier each engine task uses, per profile
Engine taskWhat it doesFastBalancedBest
chunk_extractReads each code chunk and proposes nodes and edgesfast tierfast tierbalanced tier
cross_refResolves references that span chunksfastbalancedbest
business_rulesExtracts decisions and calculationsfastbalancedbest
gap_fillRevisits inventory items nothing mappedfastbalancedbest
verifierCompares the document with your docsfastbalancedbest
  • Fast: cheapest, "good for a first look". Use it to see whether the pipeline handles your language and layout at all.
  • Balanced: "recommended for most services". Cheap model for bulk reading, stronger model for the reasoning-heavy steps.
  • Best: "highest quality, highest cost". Stronger models everywhere.
No quality benchmark yet

The profile names describe intent. There is no published comparison of accuracy between profiles, and the first measurements used different models per repository, so they cannot be compared. Choose by budget; if a result looks thin, try a stronger profile on the same project and compare the two graph versions in the Versions tab. Operators choose the actual models, so the same profile can mean different models on different deployments.

Measured so far (small repositories, one chunk each, Gemini Flash-class models): roughly a few cents per run. That does not extrapolate to large codebases, where chunking, rate limits and parallelism are untested.

CLI equivalent 
migration-agent analyze petclinic.migration --dry-run                          # prints: plan: N chunk(s), estimated cost $X
migration-agent analyze petclinic.migration --config gemini-lite.config.json --max-usd 3
# models are chosen in the config file (tasks: chunk_extract, cross_ref, business_rules, gap_fill, verifier)

07Start a run, watch it live, cancel it

Starting

On the Overview tab, Start a run offers:

Run types in the Run type menu
Menu textTypeStagesNeeds
Analyze: read the codeanalyzeingest, extract, analyzeA source. Produces the document and a new graph version.
Verify: compare with your docsverifyverifyA finished analysis (otherwise "run an analysis first") and your uploaded docs.
Re-analyze: refresh after reviewreanalyzeresolveA graph (the option is greyed out until one exists). Re-reads code around the nodes your review touched.

Then choose Model profile, set Budget cap (USD), optionally tick Incremental ("Only re-read code that changed since the last run. Unchanged code makes no model calls."), check the estimate and press Start run. The server answers immediately and queues the job; a worker picks it up.

Limits that can refuse a start (shown as a red message): another run of the same type is already queued or running ("a analyze run is already queued or running for this project"), the workspace's or your account's concurrent, monthly-run or monthly-spend ceilings, or no source yet ("upload a source archive or connect a git url first").

Watching

The panel changes to Run in progress with a status pill:

  • Progress bar: overall percentage across the stages seen so far. Stages not started yet are unknown, so the bar can look slow at first and then jump; treat it as a floor.
  • Spend / cap, Elapsed, and Stream ("Live", "Reconnecting" or "Closed"). Spend is the sum of model usage events streamed from the worker.
  • Stages: one row per stage with a done/total counter. "Waiting for the worker to pick this up." means the run is queued.
  • Log (n): expandable list of engine messages. Warnings about skipped chunks appear here.

The connection is a server-sent event stream. If it drops, the page retries up to five times with growing pauses and replays missed events, then falls back to one status read. You can leave the page: the run continues on the server, and reopening the project's Overview shows the active run again.

Cancelling

Press Cancel run in the panel (members and above). A queued run is cancelled immediately. A running run is marked "cancel requested" and stops at its next checkpoint, so the pill may say Running for a short while. What to expect:

  • Spend up to the cancellation is still metered and counts toward your limits.
  • A cancelled run does not publish its results. Stages that finished are remembered, and cached model responses are reused, so a later run does not pay for them again.
  • A budget stop is different: partial results are published.

When it ends

The panel becomes Latest run with a Start another run button. The Run history table below lists every run (started, type with profile and "incremental", status, duration, cost). A failed run shows its error in a red notice; a budget stop shows it in amber. The error text is scrubbed so it never contains the server's API key.

CLI equivalent 
migration-agent analyze petclinic.migration --max-usd 2          # runs in your terminal; Ctrl-C to stop. Re-run to resume.
migration-agent analyze petclinic.migration --workers 4          # parallel chunk calls
migration-agent verify  petclinic.migration --max-usd 1
migration-agent audit   petclinic.migration                      # per-call tokens and USD

08Read the understanding document

Open the project's Document tab (or Read the document on the Overview). Before the first successful run you see "No document yet".

  • The left column, Contents, lists the document's sections; clicking jumps to one. On the footer of that column, "graph vN" tells you which graph version the text was rendered from.
  • Each item looks like a short card: ID, name, responsibility, evidence (path:lines and symbol), confidence, module and relations.
  • Bold node IDs such as COMP-0004 or RULE-0003 are links: click one to open that node in the graph explorer with its quotes. (IDs of job, integration and dead_code nodes are not turned into links; search for them in the explorer instead.)
  • Tables scroll sideways on narrow screens. Raw HTML in the document is never rendered.
  • Items tagged preserved quirk or suspected bug are the engine's own flags. Treat them as leads for your migration plan, not verdicts.

Suggested reading order: Purpose and Capabilities for orientation, then Endpoints, Data Model and Business Rules for the parts you will rebuild, then sections 12 to 15 (Quirks, Blind Spots, Open Questions, Coverage Matrix) for what to distrust.

CLI equivalent 
less petclinic.migration/docs/understanding.latest.md       # the same document
open petclinic.migration/docs/graph.html                      # standalone interactive graph
migration-agent render petclinic.migration                     # facts-only version, no model (for checking extraction)

09The graph explorer

Open the Graph tab. On the left is a searchable list of nodes; on the right three views: Graph, Node detail and Versions.

Finding nodes

  • Search (the box with placeholder "Search name, id, file, behaviour"): the server does a case-insensitive text match across everything stored on the node (name, ID, module, responsibility, evidence file paths and quotes). It starts about a quarter of a second after you stop typing. It is substring matching, not semantic search: search for discount, a class name, a file path or an ID such as RULE-0003.
  • Type chips (group "Filter by type"): All, component, endpoint, data entity, business rule, external dependency, config. One at a time. Node types without a chip are still found by search.
  • Version menu: appears once there are two or more versions. Latest or a specific vN; list, graph and detail then all show that version.
  • The caption reports "N nodes · M loaded". The list loads 200 at a time and fetches more as you scroll to the end.

The list is a keyboard-friendly listbox: ↑ ↓ move, Home End PageUp PageDown jump, Enter selects. Each row shows the type glyph, name, ID, file and a confidence meter.

Node detail

Selecting a node opens Node detail (and puts ?node=ID in the address, so you can share a deep link). It has:

  • Header: type tag, ID, optional quirk and suspected bug flags, name, module and responsibility.
  • Confidence: the derived level and how many quotes back it (see how confidence is derived). The explanatory sentence in the app is a short paraphrase; the table in this guide is the engine's exact rule.
  • Evidence: one block per quote with file:start-end and symbol, then the verbatim code. "No quote is attached to this node." means confidence is none. This is the most important panel: open the file and check the quote.
  • Relationships: outgoing and incoming edges with edge type, a clickable neighbour and the edge's own confidence.
  • Findings that mention this node: links to the Findings tab.
  • Comments: see Comments.

The Graph view

A canvas drawing, coloured and shaped by node type. It is a visual aid; the list and detail views are the accessible path. It shows at most 400 nodes (the most connected ones) and says so: "Capped at 400 to stay responsive; narrow the filters to see others." Once a node is selected, Focus on selected neighbourhood (on by default) draws just that node's two-hop neighbourhood, up to 150 nodes. Drag to pan, scroll to zoom, click a node to select it, use the three buttons (Zoom in, Zoom out, Reset view). Labels appear for all nodes only when few are shown or when zoomed in.

Comparing versions

Open Versions. With only one version you see "Only one version so far". Otherwise pick From and To and press Compare. You get three columns, Added, Removed and Changed nodes, each with type, name and ID (clicking opens the node in the version you are looking at; removed nodes are not clickable). Use this after a re-analysis or after switching model profile to see exactly what moved.

Tip

Because IDs are stable, a node that appears under "Changed" is the same thing re-described, not a new thing. A node that vanishes and a similar one that appears usually means its symbol or module changed in the code.

CLI equivalent 
migration-agent review petclinic.migration --no-browser       # local UI on 127.0.0.1 with document, graph versions, diffs
ls petclinic.migration/graph/snapshots/                         # v001.json, v002.json ... immutable
open petclinic.migration/docs/graph.html                        # standalone interactive graph

10Add your own documentation for the Verifier

Not in the web app yet

The server has endpoints for user docs, but no page in the web app uploads them. Until it does, upload through the API (below) or use the CLI. Without docs, a Verify run has nothing to compare and the Findings tab stays at "Nothing to check".

What to upload

  • Requirements, design docs, API descriptions, runbooks, wiki exports. The more concrete the statements ("discount is 25% from 10 items"), the better the comparison.
  • Extensions accepted: .md .markdown .txt .rst .adoc .html .htm .pdf .docx .json .yaml .yml. Other types get "unsupported document type".
  • Up to 10 MB per file and 200 files per project by default. Empty files and a second file with the same name are refused ("empty file", "a document with this name already exists"). Roles member and above can add or delete.
  • PDF text extraction depends on an optional library on the server; if a PDF seems ignored, convert it to text or Markdown.
  • Secrets are redacted from docs before they reach a prompt, but do not upload documents containing credentials.

Upload through the API

# 1. get a token (the web app keeps the same token in memory)
TOKEN=$(curl -s -X POST "$API/v1/auth/login" -H 'Content-Type: application/json' \
  -d '{"email":"you@company.com","password":"..."}' | jq -r .access_token)

# 2. find your project id in the browser address: /projects/<PID>
curl -X POST "$API/v1/projects/$PID/user-docs" -H "Authorization: Bearer $TOKEN" -F "file=@requirements.md"
curl "$API/v1/projects/$PID/user-docs" -H "Authorization: Bearer $TOKEN"                   # list
curl -X DELETE "$API/v1/projects/$PID/user-docs/$DOC_ID" -H "Authorization: Bearer $TOKEN"  # remove

Then run Verify: compare with your docs. Documents are copied into the worker's scratch area per run; only the Verifier ever reads them. Uploading docs after a verify run does not change old findings; start a new Verify run.

CLI equivalent 
cp requirements.md runbook.docx petclinic.migration/user_docs/
migration-agent verify petclinic.migration --max-usd 1          # writes feedback/findings.json, prints one line per finding

The Verifier requires an existing understanding document. If verify reports nothing, user_docs/ is empty or the formats are unsupported (.pdf needs pypdf, not installed by default).

11Review findings

Open the Findings tab. A red counter on the tab shows how many are still open. The header reads "N of M open", with an Open / All switch. Findings are sorted high severity first.

Anatomy of a finding

  • Title and severity (high, medium, low), and the detail text explaining the disagreement.
  • Quotes, side by side: each shows its source (a code location or a document name) and the verbatim text. Findings whose quotes cannot be string-matched in their source are dropped before you ever see them.
  • Related node IDs: click to open the node.
Finding kinds the Verifier can raise
KindMeaning

12Comments

Comments are short notes (up to 5,000 characters) attached to something specific, and are visible to everyone in the workspace with access to the project.

  • On a graph node: in Node detail, section Comments, type in "Add context for reviewers" and press Comment. Good uses: "the VIP exception lives in pricing.py, please re-check", or "confirmed with the owning team on 3 March".
  • On a finding: expand Discussion (n) on the finding card and press Comment. This is a conversation thread for your team, separate from the formal answer.

Comments are stored with your name and time. They are also queued for the engine: at the start of the next run, unapplied comments and answers are replayed into the project, where the re-analysis can use them as untrusted hints (never as evidence). A comment on its own does not start a run in the web app; in the CLI, resolve --comment does. Viewers can read but not write comments. Comments cannot be edited or deleted in the app.

CLI equivalent 
migration-agent resolve orders.migration --comment RULE-0003 --note "Check the VIP exception in pricing.py"

13Re-analysis and incremental runs after code changes

Re-analysis after review

Triggered by The document is right and Look again, or by choosing Re-analyze: refresh after review yourself. It re-reads only the code around the nodes your review touched, merges a new graph version (IDs unchanged) and writes a changelog entry that cites the comment or answer that caused each change. The automatic run uses the Balanced profile and the server's default budget; start one by hand if you want a different profile or cap.

Incremental runs when the code has changed

The Incremental checkbox tells the analysis to re-read only chunks whose files changed (by file hash) and their dependents; unchanged code makes no model calls and IDs stay stable. It needs a previous analysis. But the engine can only see new code if the project has a new source:

There is no "replace source" button yet

A project analyses the source snapshot it already has. For a git project that snapshot was frozen at the first estimate or run. The web app only attaches a source when you create the project. To analyse newer code, call the API to attach a new source (below), which replaces the old one and clears the stored estimate, then start an Analyze run with Incremental ticked. Or create a fresh project (this loses review history).

# new git snapshot (replaces the previous source; the clone happens at the next estimate or run)
curl -X POST "$API/v1/projects/$PID/source" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"git_url":"https://github.com/org/repo"}'

# or a new archive
curl -X POST "$API/v1/projects/$PID/source" -H "Authorization: Bearer $TOKEN" -F "file=@repo.tar.gz"

After the run, open Versions and compare the last two versions to see what changed in the service. Run Verify again if you also changed your docs.

CLI equivalent 
migration-agent ingest   orders.migration --refresh      # re-copy the updated source into code/
migration-agent analyze  orders.migration --incremental --max-usd 2
migration-agent changelog orders.migration               # regenerate docs/changelog.md from snapshot diffs

18Deleting a project and what that guarantees

Open the project's Settings tab. Under Delete project and all data press Delete this project (owners and admins only), type the project name exactly into the dialog Delete this project? and press Delete forever. You return to Projects. This cannot be undone.

What is removed

  • The stored source copy and any uploaded archive.
  • The knowledge graph and all its versions, the understanding document, changelog and exports.
  • Every run, run event and artifact; findings, answers and comments; your uploaded user docs.
  • The project's saved engine state, which includes cached model responses.

How the guarantee works

The database rows are deleted in one transaction together with a "deletion task" that lists the project's file prefix. The server then deletes the files immediately. If the file store fails at that moment, the task stays and a background reaper retries with backoff until the store confirms, then writes a storage.purge audit record. A periodic sweep also removes any leftover files that no project owns. A run that was in flight when you deleted discards its results instead of recreating them.

What is not covered

  • The audit record of the deletion remains (identifiers and counts, no content).
  • Usage metering is kept for the workspace, detached from the project, so your spend history stays accurate. It contains no code.
  • Backups that the operator takes persist until they expire. Retention periods are proposed in a draft policy and are not a commitment.
  • The model provider. Excerpts of your code were sent to the configured model provider during analysis. Their retention terms apply and no zero-retention agreement is in place yet. Deleting a project cannot recall that data.
Status of verification

The deletion path is implemented and tested, but some end-to-end checks listed in the data-handling draft (against a real backend, backup expiry) are not done yet. Account deletion is not available yet as a feature.

21Reading the results honestly

This tool is a fast, cited first read of a codebase. It is not an oracle. These points come from the project's own measurements and documented limits.

What has and has not been measured

  • The pipeline has run end to end on three small open-source repositories (a Java/Spring app and two Python and Node demo apps) at a cost of cents each. Nothing has been hand-scored. There is currently no measured precision or recall for the claims it makes.
  • Those runs used different models and one hit a provider quota, so they are not comparable with each other, and say nothing about which profile is better.
  • Everything ran as a single chunk. Behaviour on 50,000 to 500,000 lines, many languages, chunk boundaries, cross-chunk references, parallelism and provider rate limits is untested. Expect those to be where trouble starts.
  • The Verifier has not yet been measured with real documentation.

What the graph counts do not mean

In the Spring example, 688 of 823 nodes were configuration keys found by static extraction, not by the model. A large node count is not a large understanding. The valuable layer, business rules and flows, is the thinnest part and the part to check hardest. In the same runs, no node reached high confidence and one language showed zero endpoints until its routing style was added to the static extractor (Django URL configuration; cross-file prefix handling has since been added for Django and Flask-RESTful but you should still check route paths).

What static analysis plus an LLM cannot see

Blind spotWhyWhat to do
Behaviour that exists only at runtimeReflection, dynamic dispatch, generated code, plugins loaded by name. The code is never executed.Expect these as blind spots or missing edges; confirm by running the system or reading logs.
Data that lives in databasesOnly code and config in the repo are read: not table contents, stored procedures that are not in the repo, feature-flag values, or reference data.Check with the data owners.
Configuration injected at deploy timeEnvironment variables, secrets, orchestration manifests outside the repo.Compare against the real environment.
Files the pipeline skipsBinaries, files over 1 MB, vendor and build directories, symlinks, withheld credential files, unparsable files (marked parse_status: fallback).Read ingest_report.json (CLI) or the Coverage Matrix and Blind Spots sections.
Languages the parser does not coverStatic extraction supports the languages that the bundled tree-sitter pack covers. Others fall back to model-only reading of text.Treat claims about such files as low confidence even if the label says otherwise.

Other services' behaviourA call to another system is an edge; what that system does is outside the repo.Analyse that service too.
Non-functional behaviourPerformance, concurrency, timing and ordering bugs are mostly invisible to reading.Use tests and profiling.
Anything that needs judgment about intent"Quirk" and "suspected bug" flags are heuristics.Ask the people who know the history.

How to use it well

  1. Verify the quotes, not the prose. The citations are the product. A claim with a matching quote at a line range is checkable in seconds. A claim in the document without a nearby citation deserves suspicion.
  2. Read confidence as "how well evidenced", not "how likely true". Low means a thin trail; high means two pinpointed quotes. Neither says the behaviour is correct in production.
  3. Read the blind-spot and coverage sections first. They tell you what the tool knows it did not map.
  4. Treat Verifier findings as questions. It sees only text on both sides and cannot tell who is right; that is why a human answers. Absence of findings is not proof of agreement: the Verifier may simply not have matched the statements.
  5. Expect run-to-run differences. Models are not deterministic. Identical re-runs reuse a cache and return the same answers; a different profile or changed code can change descriptions. Use the version diff to see what moved.
  6. Mind your data. Code excerpts go to the model provider. Redaction of secrets is best effort. Use the CLI with a self-hosted gateway if that matters.

Accepted doc / code
Resolution statuses meaning your documentation (or the code) is the truth. Only "accepted doc" re-analyses.
Audit log
Append-only record of who did what. Workspace level in the app; per-call model usage in the CLI.
Blind Verifier
The comparison step that sees only the generated document and your docs.
Blind spot
Something the tool knows it could not establish; listed in the document's section 13.
Budget cap
Hard per-run spending ceiling in USD; the run stops gracefully when reached.
Checkpoint
Per-chunk saved result that lets an interrupted run resume.
Chunk
A token-bounded piece of code the model reads in one call, cut along structural boundaries.
Coverage matrix
Table showing which inventory items (files, routes, config keys, dependencies) were mapped.
Derived confidence
Confidence computed from evidence strength rather than stated by the model.
Edge
A typed relationship between two nodes.
Entitlement
A limit your workspace's plan grants, such as projects or monthly spend.
Evidence
File, lines, symbol and a verbatim quote that supports a claim, validated against the source.
Finding
A disagreement between your docs and the code-derived document.
Graph version / snapshot
An immutable saved state of the graph; v1, v2 ...
Incremental run
An analysis that re-reads only changed code and its dependents.
Ingest
The safe, read-only copy of your source into the working project, with secrets withheld or redacted.
Inventory
The checklist of everything the analysis must account for, produced by static extraction.
Model profile
Fast, Balanced or Best: a server-side mapping from task to model tier.
Node
A thing found in the code, with an ID such as RULE-0003.
Preserved quirk
Odd behaviour flagged as worth keeping on purpose during a migration.
Reaper
The background process that retries file deletions until the store confirms them.

A targeted run that re-reads code around nodes your review touched.

Your recorded answer to a finding.

One background job: analyze, verify or reanalyze.

Run status when the cap was reached; partial results are kept.

Heuristic flag for code that looks wrong; a lead, not a verdict.

Your own documentation, read only by the Verifier.
Workspace
The team container for projects, members, usage and limits.

26FAQ

Does it run or change my code?

No. Source is copied once into a working area; nothing is executed. The model can only use read-only, path-jailed tools (read file, list directory, grep, file stat) on that copy.

Where does my code go?

Into the operator's object store, and excerpts of it (after best-effort secret redaction) to the configured model provider while a run is working. The provider's retention terms apply; no zero-retention agreement exists yet. If that is unacceptable, use the CLI with a self-hosted gateway or the offline mode, or do not analyse that code.

Can I see or choose the model?

In the web app you choose Fast, Balanced or Best; the operator maps those to models and holds the API key. In the CLI you choose models per task in a config file.

Why did my run stop before finishing?

Most often the Budget cap. The status is "Stopped at budget", partial results are published, and a new run reuses cached work. Otherwise check the run's Log and the troubleshooting table.

Will a bigger budget make it better?

Only if the run was cut short. A cap above the estimate does not buy quality; a stronger profile might, but that has not been benchmarked.

How long does a run take?

A small repository took under a minute in measurements. Large ones are limited by model-provider rate limits and have not been measured. Watch the progress panel.

Do I pay for what I spend?

Not through this product: billing is not enabled and nothing is invoiced. Your operator may pay the model provider; metered usage shows what your runs cost them, and limits cap it.

Can two people review the same project?

Yes. Everyone in the workspace with member role or above can answer findings and comment; viewers can read. Answers show the author and time. If two people answer the same finding, the latest answer is the current one.

Why does the Verifier never see the code?

So that it cannot rationalise a mismatch by reading code itself. It can only compare two texts, and the analysis never saw your docs. A disagreement is therefore independent evidence, and a human decides.

Why can't I find a node in the filter chips?

Chips exist for six of the nine types. Use the search box for job, integration or dead_code nodes, or type their ID prefix (JOB, INT, DEAD).

I deleted a project by mistake.

It cannot be restored from the app. Ask your operator whether a backup exists; otherwise re-create the project and run again.

Can I use the web app with the CLI on the same project?

Not directly. They keep separate state. You can analyse the same source in both and compare exports.

Where do I report a bug or a security issue?

Tell your operator. For vulnerabilities in the product itself see SECURITY.md in the repository.
