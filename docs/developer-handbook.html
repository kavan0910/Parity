One paragraph

The MVP: Parity takes an existing legacy application and migrates it to the newest version of its stack, or to a different technology, and proves the new app behaves like the old one. Legacy app in; migrated app, an equivalence report and a cut-over plan out. Targets covered today: Java 8 to 21, Spring Boot 2 to 3, Django 3 to 5, Express to Fastify, JavaScript to Go. Everything in this handbook serves that.

The migration has five steps: understand, approve, migrate, prove, cut over. Step 1 reads the legacy service's source code (a directory, zip, tarball or public git URL) and produces an evidence-backed understanding document (docs/understanding.latest.md, 15 sections) plus a knowledge graph. Every claim carries a file, a line range and a verbatim quote that is re-checked against the real source, and a blind Verifier compares the document with the team's own docs. In step 2 a person approves the result (decide, status, approve), which writes a migration contract. Steps 3 to 5 (chapter 14) start from that contract: plan slices, generate the new app in a sandbox, prove case by case against the running legacy app that it behaves the same, and gate the cut-over. Phase 1 is steps 1 and 2; Phase 2 is steps 3 to 5. Understanding never executes or modifies the analysed code.

It exists in two shapes that share one engine: a CLI (migration-agent, pip-installable, state in one folder), which runs all five steps, and a hosted platform in development (FastAPI backend and worker, Next.js web app, docker-compose stack), which runs step 1 today. The positioning is settled: the product is the migration; the understanding is its foundation, not an alternative product (product-architecture.md section 1).

Who it is for

Engineering teams modernising or inheriting legacy services. This is explicitly [Unknown] in product-architecture.md section 2: the first customer segment (agency doing modernisation, in-house platform team, acquirer doing diligence) is an open owner decision. Team size: one founder, so the architecture favours few moving parts (one database, one queue, one object store).

CLI users

Analysts and engineers running init / ingest / extract / analyze / verify / review on their machine with their own API key.

Hosted users (future)

Teams signing in to the web app, uploading a repo or giving a git URL, watching a run live, then reviewing findings.

You (contributor)

Three sub-projects with different toolchains: Python engine, Python backend, TypeScript web. They meet at two contracts: migration_agent.service and the /v1 HTTP API.

Design principles (the "why" behind most code)

  1. Evidence or it did not happen. Nodes and edges need file/line/quote evidence that is verified against code/; confidence is derived from evidence, never asserted by the model.
  2. Phase 1 is read-only and non-executing. The source is copied once; nothing is run; the model only gets a path-jailed, read-only tool set. Phase 2 relaxes this inside a boundary: legacy builds, generated code and test runners run only in disposable, locked-down Docker containers (14.3).
  3. The folder is the state. One project folder holds inputs, intermediate results and outputs, so a run can be resumed, diffed, backed up and audited with ordinary tools. In the hosted product this folder is packed into one tar.gz per project.
  4. Independent verification. The Verifier sees documentation and the generated document, never code; analysis never sees user docs. That separation is what makes a disagreement meaningful.
  5. Human in the loop. Findings feed a review/resolve cycle that re-analyses only what is disputed.
  6. Boring SaaS around a disciplined engine. The engine stays a pure library; the platform wraps it with conventional parts.

  • .env loading (dotenv.py): the CLI loads <repo root>/.env (the directory holding pyproject.toml, found from the installed file; falls back to cwd). KEY=VALUE, optional export, quotes stripped, # comments. Variables already in the environment are never overridden.
  • The CLI refuses a real analyze if none of ANTHROPIC_API_KEY, GEMINI_API_KEY, GOOGLE_API_KEY, OPENAI_API_KEY is set (unless --offline or --dry-run).
  • With a key, pick models with --config gemini-lite.config.json (cheapest) and always set --max-usd. Real-model scoring: scripts/e2e_live.py <config.json> (costs money, never run by pytest).

4.4 Ingest and secret handling

ingest/__init__.py: accepts a directory, .zip, tarball or git URL and writes a normalised code/. Limits: 500 MB total (MAX_BYTES), 200,000 files, compression ratio 100, 1 MB per file. Rejected: absolute or .. paths, NUL bytes, control/bidi characters in names, link escapes, special files. Skipped (and listed in ingest_report.json exclusions with a reason): .git, node_modules, vendor, build, dist, target, virtualenvs, caches, binaries (by extension), oversized files, symlinks. Git clones run with hooks disabled and a protocol allowlist; the report records source_hash (sha256 of archive bytes, or a content-tree hash for dirs/git) and commit.

ingest/secrets.py is the single choke point. Credential files (.env, .env.*, id_rsa and friends, *.pem, *.key, *.p12, *.pfx, ... except template suffixes like .example, .sample) are withheld entirely. In other files, patterns (AWS keys, GitHub/Slack/Stripe/GCP tokens, JWTs, DB URL passwords, generic api_key/secret/password/token = value, PEM private-key blocks) are replaced by [REDACTED:<kind>]. Findings hold kind and a redacted preview, never the value. Because ingest redacts code/, everything derived from it (facts, prompts, graph, docs, checkpoints) holds placeholders, not credentials. redact_string/redact_obj are reused by the audit log, user-doc loading, resolutions/comments and service._Emitter.

Hosted flow: the backend does its own archive validation and cloning (app/safety.py, app/gitfetch.py), extracts the upload into scratch, and then calls the engine's ingest with a local directory as the source. The engine's own archive/git code is mostly exercised by the CLI.

4.7 Chunker (analyze/chunker.py)

plan_chunks(code_dir, ast, context_tokens=200_000, budget_fraction=0.6, reserve_tokens=8_000) gives a budget of 200000*0.6 - 8000 = 112,000 tokens per chunk (token estimate is chars/4 plus overhead). It returns a deterministic, dependency-ordered list of Chunk (id, module, files, est_tokens, depends_on_chunks, order, partial_file, ranges).

  1. Each file is a segment if it fits the budget; otherwise _split_file splits at top-level symbol starts (_top_level_starts, from the AST facts) so a class is not cut mid-body.
  2. Segments are grouped per directory (_plan_dir, recursive over subdirectories) into _Units and packed up to the budget.
  3. _file_rank orders files dependency-first (SCC condensation with Kahn and path-order tie-break) so import chains stay contiguous and a chunk sees its dependencies' symbols already analysed.
  4. _resolve_imports derives chunk-to-chunk dependencies (JS/TS regexes, Python, Java), used for ordering and for parallel scheduling.

render_chunk_text produces the model's view: a header === path (lines a-b) === and each line as LINE_FMT = "{:>5}| {}" (right-aligned 1-based line number, pipe, text). The prompts tell the model to cite those numbers and to leave the prefix out of quotes. reanalyze.py reuses the same format.

4.8 Module analyzer, rules, merger, cross-ref, gap fill, evidence, coverage

Module analyzer (module_analyzer.py)

analyze_chunk renders prompts/chunk_extract.{system,user}.md with {{CHUNK_ID}}, {{CHUNK_TEXT}}, {{FACTS_SUMMARY}}, {{GRAPH_SUMMARY}} via render() (single-pass substitution; values are neutralized and never re-expanded). PROMPT_VERSION = "chunk_extract.v1". The model returns one JSON patch. sanitize_patch is deliberately tolerant (fills missing qualified_symbol from name/path, wraps a single evidence object into a list, drops invalid node/edge types, forces chunk_id). run_patch_task validates into ChunkPatch and on failure retries once with the validation error appended, then raises AnalysisError.

The system prompt's naming conventions are load-bearing for identity stability: module is always the repo-relative file path; component = one per file; endpoint symbol = "<METHOD> <full path>"; data_entity = one per model/table. Change them and IDs and eval scores shift.

Business rules (rules.py)

Second LLM task per chunk (business_rules, RULES_PROMPT_VERSION = "business_rules.v1") restricted to node_types={"business_rule"}; edges to non-emitted component nodes are kept.

Merger (merger.py)

merge_patches(patches, registry, base=None) is order independent: it accumulates per identity key (union of evidence sorted deterministically, set of names, longest responsibility kept, OR of quirk/suspected_bug), allocates IDs through the registry, drops edges whose endpoints do not exist (dropped_edges) and collects unresolved refs. Post-passes: dedupe_fact_endpoints (drop facts-only endpoint stubs like GET /@7 when the model produced the full-path endpoint on the same file+method within 3 lines, re-pointing edges), collapse_entity_components (merge facts-only stub components into the analysed one; a file that defines a data entity is that entity, so calls become depends_on), and with_review (replay review patches after chunk patches, blanking the older responsibility of re-emitted nodes because the merger would otherwise keep the longest text).

Checkpoint (same file) persists patches atomically under checkpoint/; chunk IDs must match [A-Za-z0-9._-]+.

Cross-reference (crossref.py)

Unresolved callee names are first resolved deterministically (match_candidates: exact name/symbol match, then suffix match on separators . :: / # :). Only ambiguous cases (up to 10 candidates, MAX_CANDIDATES) go to the cross_ref LLM task, which must pick a candidate ID or null and may never invent IDs; code snippets are shown via the read-only tools inside <<<DATA ... DATA>>> fences (fence() defangs forged markers).

Evidence verification (evidence.py)

check_evidence returns a failure reason or None: path must resolve inside code/ (and not be absolute), file must exist, the line range must lie inside the file, symbol must appear somewhere in the file (it is usually the enclosing function), and the whitespace-normalised quote must occur in the cited lines. verify_evidence drops bad evidence items; a node with none left is rejected (and its edges) unless it is a dead_code or config node with inventory_refs (KEEP_TYPES), which is demoted to file-level evidence at low confidence. Every drop is logged with a reason. assert_all_evidence_valid is the test-side gate.

Coverage (coverage.py) and gap fill (gapfill.py)

Coverage maps inventory items to nodes through inventory_refs (mapped / unmapped / excluded / complete). If incomplete, fill_gaps shows the model each unmapped item with its context (first HEAD_LINES=60 lines, or RADIUS=20 around the line) and accepts exactly one of map (new node with evidence, or an existing node id), classify (dead_code or excluded with a specific reason) or unknown. Excluded reasons feed the coverage matrix in the document. Whole-graph steps (cross_ref, gap_fill) are cached in checkpoint/extra/ keyed by a signature of their inputs, so unchanged input costs zero calls.

Failure handling in run_analyze

  • A chunk whose LLM task fails (after retries) is recorded in checkpoint/failures.json, its (possibly partial) patch is saved, the run continues; the CLI prints a warning and a re-run retries only failed/unfinished chunks.
  • BudgetExceeded and LLMAuthError (_is_stop) stop the run: in-flight parallel chunks finish and are kept, later steps (cross-ref, gap fill) are skipped, and partial results are still merged, snapshotted and rendered. The result has stopped set.
  • Parallelism (--workers N): a dependency-aware scheduler only submits a chunk when the chunks it depends on (within the pending set) have finished; completed futures are processed in chunk order, so the merge stays deterministic.

4.9 Incremental analysis (analyze/incremental.py)

Workflow: ingest --refresh (replaces code/) then analyze --incremental. checkpoint/manifest.json stores per-file SHA-256 hashes, import deps, chunk signatures, prompt_version and model. plan_reuse decides which saved patches survive:

  • No manifest → analyse everything. Prompt version changed ("chunk_extract.v1|business_rules.v1") → analyse everything.
  • Default (resume) mode: a chunk is reused when the same chunk ID has an identical signature.
  • Incremental mode: changed/added/removed files are "dirty", plus every file that imports a dirty file (dependent_files, from both new and old deps); chunks containing a dirty file are re-analysed; others are matched by signature even if chunk IDs were renumbered, and their patches are re-keyed.

Cumulative cost across sessions lives in audit/cost_total.json (record_session_cost); the CLI prints "this session" and "project total".

Only the chunk and rules prompt versions are in the manifest. Editing crossref.py/gapfill.py/verifier prompts does not invalidate chunk patches (their caches key on input signatures instead). If you change the chunk or rules prompts, bump PROMPT_VERSION / RULES_PROMPT_VERSION or old checkpoints and the LLM disk cache will keep serving old behaviour.

What complete() does, in order

  1. Cache lookup: key sha256(model \0 system \0 prompt \0 prompt_version) → llm_cache/<key>.json. Hit → return with cached=True, cost_usd=0, audited.
  2. Budget check before the call: estimated input (chars/4) plus the full max_output_tokens priced; raises BudgetExceeded if spent + est > max_usd (Budget is thread-safe).
  3. Call with retries (_with_retries): errors are classified (_kind): timeout, rate_limit, overloaded (503/529), server, connection are retryable; auth → LLMAuthError; not_found / bad_request are not retried and get an explanatory note. Delay honours a provider Retry-After/retryDelay up to max_retry_after seconds; otherwise capped exponential backoff with jitter. A rate-limit that looks like a daily quota or asks for a wait longer than max_retry_after raises QuotaExhausted immediately instead of sleeping for hours.
  4. Fallback model: after retries are exhausted on a retryable kind, move to fallback_models[model] (chains allowed, no cycles).
  5. JSON repair: if json_mode and the reply does not parse, one repair call with the bad reply and REPAIR_INSTRUCTION; both calls are paid for.
  6. Cache write (atomic, only when the JSON parsed), budget update, audit record (llm_call: model, tokens, USD, prompt_version, input_hash, task, cached).

For Claude models the system message carries cache_control: ephemeral (provider-side prompt caching). Gemini configs raise retries to 8 and backoff to 5-90 s because free tiers are tight.

llm_cache/ is keyed by prompt content, not by tenant. Two tenants with identical code would share responses. Hosted rule: the cache lives inside each project's own state archive (per project, therefore per workspace, deleted with the project); never share one cache directory between tenants, and use pack_project(include_cache=False) for any export. Also treat it as sensitive: it contains model output derived from customer code.

Budget accounting is layered: the client's Budget (pre-call estimate), analyze.runner._Metered (post-call, raises when usd >= max_usd) and service._EventLLM (usage events). With workers > 1 one in-flight call per thread can overshoot max_usd slightly (NOTES-service.md).

4.11 Sandbox tools and the process guard (sandbox/)

Two layers; know which one you rely on (sandbox/README.md).

  • Layer 1, the container (the real boundary): read-only rootfs, source mounted :ro, noexec tmpfs scratch, no network (profile offline) or egress only through an allowlisting Squid proxy to one host (profile model), cap_drop: ALL, no-new-privileges, uid 10001, pids/memory limits, no credentials in the image.
  • Layer 2, in-process:
    • ReadOnlyTools(root) (tools.py): the only thing the model can use. read_file, list_dir, grep, file_stat. Paths are resolved with symlinks followed and must stay under root (.., NUL, outside absolute paths, escaping symlinks raise SandboxViolation). Caps: file 2,000,000 bytes, 2000 lines per read, 2000 chars per line, 200,000 output chars, 1000 list entries, 200 grep matches, 5000 grep files, 500-char patterns; binary files refused. No write, exec or network method exists: enforced by construction.
    • enforce_readonly_process(SandboxPolicy(allowed_hosts, write_dirs)) (guard.py): irreversible per process; audit hooks plus patched socket functions block non-allowlisted connects/DNS, writes outside write_dirs, mutating os/shutil calls and process spawn. Raises GuardViolation (a PermissionError).

The guard is a tripwire, not a boundary: ctypes/native code, open file descriptors, mmap and /proc/self/fd tricks bypass it, reads are not restricted by it, and the allowlist is by host not port. Its tests run in subprocesses so audit hooks do not leak into pytest. Do not describe it as isolation.

4.12 Verifier, review, resolve, changelog

Blind Verifier (verify/)

Item IDs are filtered to the [A-Z]{2,5}-\d{4} pattern. code_only findings are grouped by module directory (_area_of) into one finding per area. Findings are sorted by severity, kind, area, title and numbered F-0001.... Kinds: contradiction, doc_only, code_only, doc_vs_doc; severity low|medium|high. Review loop (review/)

  • comments.py: comments attach to a graph node or edge ID, have processed flag.
  • reanalyze.py: targeted: for each affected node (from pending resolutions' affected_node_ids and unprocessed comments) it re-reads only the code around its evidence (MARGIN=40 lines, merged windows), asks the model (task chunk_extract, prompt reanalyze.v1) with the reviewer note wrapped in <<<USER_NOTE_BEGIN>>> markers as untrusted data, merges onto the old graph, re-verifies evidence, saves a new snapshot, stores the patches in checkpoint/review/vNNNN.json (so later analyze replays them), marks comments/resolutions processed/resolved, appends to feedback/reanalysis_log.json. If the budget stops it, nothing is written (ReanalysisResult.stopped).
  • changelog.py: docs/changelog.md from consecutive snapshots (## vN (from vM), trigger, Added/Changed/Removed with evidence and the why from the reanalysis log).

Local review server (review_ui/server.py)

5.7 Run lifecycle, job queue and worker

Creating a run (services/runs.create_run)

  1. Validate type (analyze | verify | reanalyze), model_profile (fast | balanced | best), 0 < max_usd <= HARD_MAX_USD (default DEFAULT_MAX_USD). analyze needs a source (409 no_source); verify/reanalyze need an existing document artifact (409 no_analysis).
  2. Admission control: lock_row on the user row, then on the workspace entitlement row (fixed order, no deadlocks); everything below is re-read after the locks. Idempotency-Key replay returns the existing run (HTTP 200). Then a queued/running run of the same type → 409 run_in_progress; can_start_run (workspace) and can_user_start_run (per user) → 403 entitlement_denied.
  3. Insert the run inside a savepoint; the partial unique index is the final arbiter (IntegrityError → 409). Then jobs.enqueue, event status: queued, audit run.create.

Queue (jobs.py)

  • claim: Postgres SELECT ... FOR UPDATE SKIP LOCKED; SQLite a single atomic UPDATE ... WHERE id = (SELECT ...) RETURNING id. Sets running, locked_by, locked_at, attempts+1.
  • heartbeat refreshes locked_at; reap_stale(timeout) re-queues (or fails with "worker lost" when attempts are exhausted) running jobs whose heartbeat is older than JOB_LOCK_TIMEOUT_S (600 s) and releases the project lock.
  • try_lock_project/unlock_project: compare-and-set on projects.active_run_id so only one run executes per project (its state is a single archive). A second job for the same project is pushed back 5 s with its attempt count refunded.
  • backoff_delay(attempts, base) = min(900, base*2^(attempts-1)) with +/-20% jitter.

Worker (worker.py, python -m app.worker)

Loop: periodically run the deletion reaper (every REAPER_INTERVAL_S, with orphan reconcile every RECONCILE_INTERVAL_S), reap stale jobs, claim a job, process it, sleep WORKER_POLL_S when idle. The loop survives DB errors. SIGINT/SIGTERM set a stop event. The worker runs with bypass_rls=True (app.bypass=on): a trusted service principal.

STAGES: analyze → (ingest, extract, analyze), verify → (verify), reanalyze → (resolve). _execute:

  1. Mark running (started_at, engine_version), build the engine config from the profile (profiles.engine_config: model per task tier, api_base, api_key from server settings).
  2. Create a scratch dir (0700, always removed); if the stored state tar.gz exists, unpack_state into it; replay un-applied API comments and resolutions into the engine folder (_apply_review: engine.add_comment/add_resolution, then mark applied, even on error so a vanished item is not retried forever).
  3. For each stage not already in completed_stages: check cancellation/deletion; skip ingest if stored state already holds the same ingested_source_id; compute remaining budget; emit stage started; call engine.run_stage(pdir, stage, config=cfg, max_usd=remaining, workers=ENGINE_WORKERS, offline=ENGINE_OFFLINE, on_event=sink, ...); reconcile any engine cost not streamed as usage events (task unattributed); on ok mark the stage done and upload the packed state (so a retry can resume on any worker); on stopped_budget break and publish partial results; on error text matching a transient marker (timeout, 429, 503, overloaded, connection ...) raise RetryableError, else fail.
  4. Publish results (materialize.publish_results): state, document, changelog, review_state, graph versions (immutable: existing versions not rewritten), per-version snapshots, graph.html.
  5. _finish sets the terminal status, writes a status event, audit run.finish, calls billing.report_usage (no-op), always unlocks the project. Retry path: job back to queued with backoff, run back to queued, event status: retrying; attempts exhausted → failed.

Budget per stage = min(run.max_usd - spent, monthly remaining excluding this run's reservation) so parallel runs cannot each take the whole monthly remainder. EventSink bridges engine callbacks (any thread) to the DB: progress throttled to one write per 0.25 s, usage rows + run cost increment, logs scrubbed of the API key; it heartbeats every 10 s and every 2 s checks for cancel/deletion (surfaced at the next stage boundary). A daemon thread also heartbeats every max(1, JOB_LOCK_TIMEOUT_S/4) s.

Cancellation and deletion are honoured between stages only; the engine has no cancel hook, so a long analyze stage continues until it finishes or hits max_usd. A worker killed mid-stage re-runs that stage after the reaper timeout (state from the previous stage is reused). ENGINE_OFFLINE must never be set in production.

Deletion queue (services/deletion.py)

delete_project deletes rows (events, jobs, artifacts, comments, resolutions, docs, sources, runs, project), detaches usage_events, writes the project.delete audit record and a deletion_tasks tombstone in the same transaction, then tries the store immediately. On failure the worker's reap retries with exponential backoff (30 s base, 1 h cap) until the store confirms, then audits storage.purge. reconcile_orphans queues any {workspace}/{project}/ prefix in the store that has no project row (write-object-before-row races, worker deleted-during-run path).

5.8 SSE (GET /v1/runs/{rid}/events)

The handler is async on purpose (pentest F1: a sync generator with time.sleep let ~40 open streams starve the threadpool and /healthz). It authenticates in a short session that is closed before streaming, then polls with asyncio.sleep(SSE_POLL_S) and short run_in_threadpool reads.

  • Wire format: id: <seq>, event: <type>, data: <json payload>. Types: status, stage, progress, usage, log, final end ({status} or {status:null, reason:"lifetime"|"revoked"}). : ping comments every 15 s when idle.
  • Resume: ?after=<seq> or Last-Event-ID replays stored events.
  • Caps: SSE_MAX_PER_USER (5) and SSE_MAX_PER_RUN (20) → 429; SSE_MAX_LIFETIME_S (3600) ends with reason: lifetime and the client reconnects; every SSE_RECHECK_S (10 s) the token and membership are re-validated, a removed viewer gets reason: revoked. Caps are per API replica (limits.SseRegistry, leases with a deadline).
  • Scalable fix not built: Postgres LISTEN/NOTIFY instead of polling.

5.9 Ingestion safety (safety.py, gitfetch.py)

Git URLs (validate_git_url)

  • https only, max 2000 chars, no control characters or backslashes, no credentials, no query string, port 443 only, host restricted to LDH characters (punycode only), trailing dot stripped; localhost, metadata hosts and suffixes such as .local .internal .lan .corp refused; numeric host spellings (decimal, hex) refused.
  • DNS is resolved and every A/AAAA address must be public (ip_is_public: is_global and not in an extra blocklist covering private, CGNAT, link-local, cloud metadata, IPv4-mapped/compatible, NAT64, 6to4, 100::/64, ...). Unresolvable and non-public hosts give the same error.
  • Optional host allowlist GIT_ALLOWED_HOSTS. The URL handed to git is rebuilt from the validated components so the DNS-pin key and the connect host cannot diverge.

Clone (clone_public_repo)

Hardened shallow clone: -c core.hooksPath=/dev/null, protocol.allow=never + protocol.https.allow=always, http.followRedirects=false, http.curloptResolve=host:443:addrs (DNS pinning), no submodules, --depth 1 --single-branch --no-tags; minimal environment (GIT_TERMINAL_PROMPT=0, GIT_ASKPASS=/bin/false, empty global config; only the https proxy variables are forwarded); own process group, wall-clock timeout GIT_TIMEOUT_S, size and tree-shape watch while cloning (check_tree, GIT_MAX_MB); afterwards .git removed, symlinks stripped, file-count cap. Pinning does not apply through a proxy (the worker); there the proxy's domain allowlist is the control.

Archives (extract_archive, ArchiveLimits)

Zip and tar.gz: zip-slip, absolute/backslash/drive paths, links and special files, encrypted zips, duplicate names, per-file and total size counted from the real stream (headers are not trusted), compression-ratio cap, file-count cap, depth cap, wall-clock cap, and every member including directories counts toward MAX_ARCHIVE_ENTRIES (the F3 tar directory-bomb fix). Request bodies are capped by BodyLimitMiddleware: 1 MiB by default, MAX_UPLOAD_MB + 2 MiB for paths ending /source or /user-docs. 5.12 Limits and rate limiting

  • ratelimit.TokenBucket: in-process token bucket per key (IP for unauthenticated/auth routes, user id for authenticated routes). 429 rate_limited with Retry-After.
  • LoginThrottle over an AttemptStore (5.3). Limiter and AttemptStore are protocols; make_limiter/make_attempt_store are the seam for a shared store. Only in-memory implementations exist, so every limit (rate, SSE, estimate slots, login throttle) is per process; with N replicas the effective limit is N times higher.
  • Client IP: the TCP peer unless TRUST_PROXY_HEADERS, then the TRUSTED_PROXY_COUNT-th entry from the right of X-Forwarded-For (fewer entries than expected means use the peer). uvicorn's proxy rewriting is off (--no-proxy-headers). Wrong either way and you collapse all users into one bucket or let clients spoof an IP.
  • limits.SlotLimiter: estimate slots, per workspace (1) and global (3); beyond that 429.

5.13 Error envelope, logging, security headers

Every error is {"error": {"code", "message"}} (errors.py). Raise ApiError(status, code, message, headers); helpers not_found(what), forbidden(msg). Handlers also convert Starlette HTTP errors (bad_request, unauthorized, forbidden, not_found, method_not_allowed, conflict, payload_too_large, rate_limited), validation errors (422 invalid_request, first 5 messages), IntegrityError (409 conflict: a lost race is never a 500) and anything else (500 internal_error, logged by exception type only). Domain codes: invalid_source (422), entitlement_denied (403), no_source, no_analysis, run_in_progress (409), signup_disabled (403), engine_error (502).

Logging (logging_setup.py): JSON lines with ts, level, logger, msg, request_id, run_id and for access logs method, path (no query string), status, duration_ms, user_id. Policy: never log bodies, Authorization headers, API keys, source content or archive file names. Text mode escapes CR/LF and control characters. X-Request-Id is accepted if alphanumeric/-_ up to 64 chars, else generated. Run events scrub the model key. Security headers on every response: X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY, Cross-Origin-Resource-Policy: same-site, Permissions-Policy, CSP default-src 'none'; frame-ancestors 'none'; base-uri 'none' (not on /docs), HSTS in production.

6.3 SSE client

EventSource cannot send an Authorization header, so api.runs.stream uses fetch + body.pipeThrough(new TextDecoderStream()) and lib/sse.ts::SseParser, an incremental parser that handles \n, \r\n and \r endings (holding back a trailing \r), comments (: ping), multi-line data, event and id. The server names the event in the SSE event: field and omits type from the JSON, so the client merges them: type = data.type ?? (event === "end" ? "status" : event) and copies id into seq.

lib/runState.ts has the pure reducer reduceRunEvent (RunLive: per-stage progress, order, accumulated cost and tokens, last 200 log lines, status, error, lastSeq). Events with seq <= lastSeq are ignored, which makes replay after reconnect idempotent. Non-terminal markers (retrying, cancel_requested) never overwrite the real status. overallPercent is a floor (stages not yet started are unknown; default 4 planned stages).

The stream ends after the server's end event or after 1 hour (reason: lifetime); the client must reconnect with the last seq. Check RunPanel.tsx for how reconnects are handled before assuming it resumes a 2-hour run: I did not verify long-run reconnect behaviour end to end.

6.5 Graph explorer: design and performance

  • Server-side filtering and paging. useGraphList(pid, {version, type, q}) fetches pages of PAGE = 200 nodes; any filter change bumps a generation counter and resets the list, so stale responses are discarded. loadMore is guarded against double calls.
  • Virtualised list. VirtualList renders only visible rows (fixed row height, overscan 6) as an ARIA listbox with aria-activedescendant, aria-posinset/setsize, keyboard Arrow/Home/End/PageUp/PageDown/Enter, and triggers onEndReached. It handles the 5,200-node mock project.
  • Canvas graph is a visual aid, the list and detail view are the accessible path. GraphCanvas draws type-specific shapes with pan/zoom/hover/select. graphLayout.layoutGraph is a small deterministic force-directed layout (initial ring per node type seeded by a string hash, so the same input gives the same picture; O(n^2) repulsion; 90 iterations above 300 nodes, else 160). Because of the O(n^2) cost the explorer shows at most MAX_GRAPH_NODES = 400 (top by degree via topByDegree, then induced edges) and says so in the UI. Layout is memoised on the node/edge set, not on selection.
  • lib/graphFilter.ts: AND-of-terms case-insensitive match over id, name, module, symbol, responsibility, type; confidence rank filter; flagged-only (quirk or suspected bug); countByType.
  • NodeDetail shows evidence quotes in a "ledger" block with the derived confidence explanation, relationships, related findings and a comment box; GraphDiffView shows added/removed/changed nodes between versions.

Known limits: layout runs on the main thread (~100 ms at 400 nodes); beyond that needs server-side sampling or a worker/WebGL renderer. Node counts per type for filter chips are not available from the API, so chips show no counts.

9.3 Eval harness and regression gates

eval/repos/{express-crud (18 files), spring-lite (11), django-lite (8)} each have a hand-labelled expected.json: nodes {type,name,module,qualified_symbol} (categories components, endpoints, entities, rules), edges ({type,source,target} as identity keys type|module|qualified_symbol), rules with evidence ranges verified against the repo, and for express-crud must_not_appear canaries (prompt-injection strings planted in src/vendor/legacy-notes.js). evalharness.score(actual, expected, repo_dir) returns per-category precision/recall/F1 with missed/spurious lists plus gates.

  • Gate 1: evidence validity must be 100% (every cited file/line range exists in the repo).
  • Gate 2: no must_not_appear string may appear in any actual node/edge text.
  • Regression: compare(old, new) fails if any category F1 drops (default tolerance 1e-9) or a gate newly fails. The e2e golden score check allows a drop of at most 0.05 (per its README).
PYTHONPATH=src python scripts/score.py my.migration django-lite -v      # score a project's latest graph
UPDATE_GOLDEN=1 PYTHONPATH=src python -m pytest -q tests/e2e            # regenerate goldens after an INTENDED change
git diff tests/e2e/golden                                              # review what moved before committing

Goldens: graph.schema.json (exact), doc.headings.json (exact), <repo>.findings.json (exact), <repo>.score.json (via compare). Without UPDATE_GOLDEN a missing golden fails with a hint instead of being created silently. One known bug is encoded as a non-strict xfail: test_edge_ids_survive_review_cycle (re-analysis re-allocates IDs for edges rewritten by collapse_entity_components); remove the marker when fixed.

The eval repos are tiny, and the e2e suite replays answers derived from expected.json, so a green e2e proves the plumbing, not model quality. Prompt or model changes can only be judged with e2e_live.py.

11Conventions, gotchas and landmines

Collected from the NOTES files, docstrings and code. Read this section twice.

11.1 Engine

  • llm_cache/ is keyed by prompt content, not tenant. It must stay per project, never shared across tenants (SEC-1). Treat it as sensitive; exclude it from exports (include_cache=False).
  • Confidence is derived. Never store or trust it; parse_graph strips it on load.
  • Identity is (type, module, qualified_symbol). Any change to how modules/symbols are named (prompt conventions, extractor route names) renames nodes, allocates new IDs and breaks reviewer references. IDs are never reused.
  • Django path() names are kept verbatim; join_path strips trailing slashes and empty segments. Both are pinned by tests and recorded eval graphs.
  • Facts-only stubs are recognised by the responsibility prefix "(facts only". Do not change that text without updating merger.py.
  • Bump PROMPT_VERSION / RULES_PROMPT_VERSION when chunk or rules prompts change; the verifier/reanalyze/crossref/gapfill prompts are not part of the manifest.
  • render (CLI) creates a new, facts-only snapshot. Snapshot version numbers only ever go up.
  • Budgets are estimates before the call and actuals after; --workers > 1 can overshoot slightly. A run stopped by budget keeps partial results; a re-analysis stopped by budget writes nothing.
  • service.run_stage returns failed instead of raising; only an unknown stage raises. Hosted reanalyze=False by default (CLI default True). service never reads MA_* env.
  • audit.py imports fcntl: POSIX only. File locks and atomic writes assume a local disk.
  • Posix paths in evidence and IDs: always repo-relative with forward slashes.
  • .pdf user docs need pypdf, which is not installed by default; the Verifier silently skips them with a log warning.
  • Secrets: [REDACTED:kind] placeholders in code/ mean evidence quotes of those lines contain placeholders, not the original text; quotes are verified against the redacted copy.

11.2 Backend

  • Use the tenancy dependencies; foreign resource = 404, role shortfall = 403.
  • Cancellation and project deletion are honoured only between engine stages (no cancel hook in the engine).
  • Entry point is the factory app.main:app_factory with --factory. Run pytest from backend/.
  • /estimate runs ingest+extract inside the API process (reads customer code in the API tier and may git clone from the API host). Known deviation; moving it to a worker job is not straightforward because the response is synchronous.
  • Worker kills mid-stage re-run that stage after the reaper timeout. ENGINE_OFFLINE must never be set in production.
  • Limits (rate, SSE, estimate slots, login throttle) are per process; behind N replicas multiply.
  • Comment text is stored raw in the DB (the engine redacts its own copy).
  • DNS pinning relies on libcurl honouring http.curloptResolve (git >= 2.37) and does not apply via a proxy.
  • Results are read whole from the object store per request; graph search is a substring match over node JSON.
  • The LLM cache lives inside each project's state archive (per project, therefore per workspace and deleted with the project) instead of a shared per-workspace cache (a deviation from the contract text).
  • usage_events survive project deletion (detached); audit_log has no FKs on purpose.
  • A new source replaces the old one and clears the stored estimate, so the web must re-estimate.
  • backend/README.md is stale in places (migrations list, SIGNUP_ENABLED default). Trust config.py.
  • Signup passwords need at least 10 characters (server-enforced; I did not find a matching client-side check). The web client's archive validator allows 200 MB (lib/validate.ts) while the backend default upload cap is 100 MB (MAX_UPLOAD_MB, also bounded by the plan's max_source_mb): the server wins.

11.3 Web, deploy, process

  • NEXT_PUBLIC_* is baked at build time; a running container will not see changes.
  • Components must not call fetch; extend lib/api.ts and the mock together.
  • EventSource cannot send auth headers: use the fetch-stream client.
  • Token is memory-only: a reload logs you out in real mode (mock mode persists in sessionStorage).
  • Graph view caps at 400 nodes by design (O(n^2) layout on the main thread).
  • deploy/postgres-init/10-roles.sh runs once per fresh volume; production refuses placeholder secrets, so a copied .env.example will not boot.
  • Squid allows by domain only; GIT_ALLOWED_HOSTS empty means the worker cannot clone.
  • Two separate Docker setups: docker/ (engine batch image) and deploy/ (platform stack).
  • CI has never run; the backend workflow references extras that do not exist. Do not assume green means anything yet.
  • macOS: this repo sits in ~/Downloads, which is TCC-protected; tools launched from some terminals fail with "Operation not permitted".
  • Do not commit .env, deploy/.env, *.db, data/store. Never write secrets into docs or tests (test fake secrets contain EXAMPLE).
  • Honesty rule for docs: no claims of certifications or audits that do not exist; keep "unverified" markers until something has actually been run.

11.4 Code conventions seen in the repo

  • Python 3.11+, from __future__ import annotations, pydantic v2 with extra="forbid" on model-facing types, type hints throughout, small functions, docstrings that explain why.
  • Atomic file writes (temp + os.replace) for anything persisted; deterministic output (sorted keys/IDs) so diffs and goldens are stable.
  • Defensive extractors: never raise, degrade to [].
  • Error text that may reach users is scrubbed of secrets (redact_string, _scrub).
  • Backend: one concept per module, services return domain results, routers translate to HTTP; ApiError for expected failures.
  • Web: strict TS, no UI framework, small accessible primitives, tokens as CSS variables, pure logic in lib/ with unit tests.
  • Commit style in history: imperative summaries of what changed and why.

  • The running legacy service is the oracle. Expected outputs are recorded from it (twice, to derive noise masks), never written by the model, except for behaviour you decided to fix, and only after tests approve-spec.
  • Slices. The planner turns the approved graph into ordered slices (foundation, entry points, bootstrap); every in-scope node lands in exactly one slice and slice IDs are stable across re-planning.
  • Generation loop per slice: context pack, validated model edits, commit in target_code/, sandbox build, unit tests plus the characterization suite against the new service, fresh-session review, then awaiting_human. Failures feed a fix iteration up to --max-iterations (4); then the slice is blocked. Every step is a file under slices/SLICE-NNNN/iterations/K/, so a killed run resumes and loses at most one model call.
  • Equivalence classifies each difference as match, noise, intended_divergence, regression or unknown. Regressions become fix requests that the next generate picks up; triage can also produce legacy_bug (a decision for you), harness_issue (a mask proposal) and spec_ambiguity (blocks the slice).
  • You approve each slice. approve-slice is refused unless the contract gate passes, the build and suite are green, the equivalence report has no regression or unknown diff, target_code HEAD is unchanged since that run, and all blockers are cleared.
  • Advisory checks beside the gate. Every equivalence run records per-case latency on both sides and flags cases where the new service is much slower; equivalence fuzz mutates recorded HTTP cases and compares both services (migrate/differential.py). Neither blocks approval; cutover shows them as warnings.
  • Cut-over is a plan, not a deployment. cutover checks readiness and writes a deterministic cutover/plan.md; --approve pins hashes of the contract, plan, code and every equivalence artifact.

14.5 Budget, resume and the slice state machine

  • Budget. target init --budget-usd N sets a project budget. ledger.py derives cumulative spend from audit/audit.jsonl, and every model call is capped by what remains, plus per-run (--max-usd) and per-slice (--max-usd-per-slice) caps.
  • State machine. Slice status changes only through state.transition (slices/SLICE-NNNN/state.json): the statuses (planned, tests_recorded, generating, built, tests_passing, reviewed, awaiting_human, approved, rejected, blocked, ...) and the allowed transitions are defined in TRANSITIONS and validated.
  • Humans can edit. You may commit to target_code/. generate refuses a dirty tree and never overwrites uncommitted edits; a commit after the last equivalence run makes approval wait for a new run. Human commits feed the human-edit metric.
  • Metrics. metrics derives cost per slice, node and 1k legacy lines, cache hit rate, iterations to green, first-try build success, characterization pass rate, equivalence %, unknown-diff rate, mask additions, human-edit rate and wall-clock split from existing files only. A metric without data is n/a, never 0.

14.6 Authenticated and stateful services

Found by the first live run: the sandbox generated a random API token per run and nothing sent it, so every recorded case of a token-protected service was a 401, and the documented seed replay did not exist. What the harness does now (migrate/harness.py):

  • request_headers on a service, e.g. X-API-Token: "{secret:API_TOKEN}". request_headers_for() resolves {secret:NAME} from the values written at harness up (NAME must be in synthetic_secrets) and run_cases_in_network passes them as the runner's extra_headers. A case header overrides an injected one case-insensitively, and an empty value removes it (harness_runner/wire.py: merge_headers), so a "no token" case is expressible.
  • seed_requests (a JSON file in the legacy source) is replayed by replay_seeds() after every up: for legacy, new, and directly against both services of the composite. A seed must answer below 400 or one of its expect_status; a failure stops up and tears the harness down.
  • Same state before comparing. equivalence and equivalence fuzz call harness.restart() on each harness-mode side first (--no-reset to keep state), so both start from the same seeded data.
  • Timestamps. json_equal in harness_runner/jsonpath.py treats two ISO-8601 timestamps within 300 s as equal: two instances seeded moments apart never agree on "now". Hours apart, or zoned against naive, still differs. One place, so recording, equivalence, fuzzing and the composite agree.

14.8 Known gaps and rules for contributors

  • No stage has run with a real model; quality of generated code is unmeasured. The offline proposer’s cases miss boundary changes (a seeded price <= 0 to price < 0 change went unnoticed), and the fuzzer only mutates fields already in recorded bodies.
  • Images (runner, router, proxy, codemods) are tags, not digests (each run records the digest it used). gVisor and OpenRewrite through Gradle have not run.
  • gRPC and message characterization cases return not_implemented. Lockfile hashes and a CycloneDX SBOM are recorded per build (migrate/supplychain.py) but a package whose hash differs is not refused.
  • With in-memory sqlite or none DB engines the composite gives each service a private database (db_shared: false): an in-memory database cannot be shared. Use postgres or mysql to test a shared one.
  • Reviewer precision needs your verdicts (slice review-finding); the Cut-over tab exists in the review UI.
  • Phase 2 is CLI and self-hosted only (decision P2-Q13). The hosted worker must not run it. Do not add Phase 2 stages to the hosted job path without redoing the threat model.
  • Rules the live runs taught: never put a tmpfs workdir over a path the command uses (the backend now refuses it); /tmp is noexec, so tools installed there are started through their interpreter; Maven ignores HTTPS_PROXY; npm needs a writable HOME; a tool that exits 0 on failure needs its output checked.
  • Change migrate/models.py only additively; never fork MigrationContract; never pass real secrets or model keys into a container; never pull images from the exec backend.
